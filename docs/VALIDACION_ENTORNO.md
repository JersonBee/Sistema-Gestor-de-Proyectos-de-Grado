## Límites de esta validación

- En el primer intento Docker Desktop no tenía un motor disponible. En el reintento se identificó un socket interno inaccesible (`sailor-ingest.sock`). Una detención limpia retiró el socket y permitió arrancar. No fue necesario renombrarlo ni borrar datos de Docker.
- La primera construcción del contenedor encontró que Maven Wrapper cambiaba a TAR al no disponer de `unzip`, lo que no correspondía al checksum ZIP fijado. Se añadió `unzip` únicamente a la etapa de compilación y se conservó la comprobación SHA-256. La siguiente construcción finalizó correctamente.
- Docker Desktop se actualizó automáticamente de 4.87.0 a 4.95.0 durante la prueba y reinició el motor. Se comprobó nuevamente el servicio tras ese reinicio: Docker Engine 29.8.2, contenedor activo y pruebas HTTP correctas. No se inició manualmente una instalación de actualización.
- El conector NIO de la instalación Java local falló al crear un socket interno; NIO2 permitió ejecutar las comprobaciones. Este ajuste solo se hizo en el servidor temporal de pruebas, no en el contenedor Linux.
- Se verificó conexión JDBC real al esquema `grado` en Supabase mediante Session Pooler con TLS `verify-full` y la CA oficial. El endpoint directo solo resolvía por IPv6 desde este entorno.
- Se aplicó `006_acceso.sql`, una migración aditiva para sesiones, límites de intentos de acceso y funciones de registro/autenticación. No se borraron datos ni se crearon cuentas de prueba en Supabase.
